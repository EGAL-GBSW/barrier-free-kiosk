# 대화형 메뉴 탐색·조건 추출 설계 초안

이 폴더는 기존 9개 메뉴를 AI가 참조할 JSON으로 정리하고, 김영수 할아버지(74세, 가상 인물)의 대화 시나리오와 조건 추출 정답 40개를 정의한다. Ollama를 통한 로컬 SLM 추출과 대화 컨트롤러가 연결되어 있으며 [A4000 Windows 텍스트 테스트](../TEXT_DIALOGUE_WINDOWS.md)로 실행한다. STT/TTS·실제 주문 API는 아직 연결하지 않았다.

## 파일과 데이터의 확정 범위

| 파일 | 내용 | 사용 범위 |
|---|---|---|
| `menu_catalog.json` | 최신 백엔드의 9개 메뉴와 대화용 추가 필드 | 백엔드 값은 그대로 복사, 추가 속성은 매장 확인 필요 |
| `demo_attributes.json` | 시나리오 검증을 위한 우유·카페인·단맛·사이즈 가정 | `demo_only`, 운영 주문에 사용 금지 |
| `extraction.schema.json` | 모델이 반환할 JSON 구조 | 형식 계약, 해석 정확성을 보장하지 않음 |
| `utterance_examples.jsonl` | 입력 발화·이전 상태·조건 추출 정답·후속 행동 | 사람이 작성한 예시, 학습·평가의 초기 기준 |
| `validate_assets.py` | 데이터 검증, 정답 조건으로 필터 시연, 모델 입력 미리보기 | Python 표준 라이브러리만 사용, 모델 호출 없음 |
| `ollama_client.py` | 로컬 SLM 요청, JSON 형식·ID·발화 근거·설명 인용 검증 | Ollama Chat API의 JSON Schema 출력 사용 |
| `conversation.py` | 메뉴 형식 정규화, 상태 관리, 질문·후보·확인·테스트 장바구니 | 실제 주문 전송 없음 |

백엔드 원본은 `backend/src/data/menus.js`, 기준 커밋은 `451449d`이다. 여기서 확인된 값은 실제 매장의 별도 승인 여부가 아니라 **저장소에 등록된 값과의 일치**를 뜻한다.

| ID | 메뉴 | 기본 가격(원) | 카테고리 | 등록된 온도 |
|---:|---|---:|---|---|
| 1 | 아메리카노 | 3,000 | coffee | ICE, HOT |
| 2 | 바닐라 크림 라떼 | 4,900 | coffee | ICE, HOT |
| 3 | 카페 라떼 | 4,200 | coffee | ICE, HOT |
| 4 | 제주 말차 라떼 | 5,200 | noncoffee | ICE, HOT |
| 5 | 리얼 딸기 밀크 | 5,500 | noncoffee | ICE |
| 6 | 딥 초코 프라페 | 5,800 | frappe | ICE |
| 7 | 생딸기 케이크 | 6,500 | bakery | 선택 정의 없음 |
| 8 | 버터 크루아상 | 3,800 | bakery | 선택 정의 없음 |
| 9 | 바스크 치즈케이크 | 5,900 | bakery | 선택 정의 없음 |

우유·카페인·단맛의 구조화된 확정값, 사이즈, 옵션 추가금, 판매 가능 상태는 현재 백엔드에 없다. `menu_catalog.json`에서는 이 항목을 `null`로 둔다. 상품명·설명에서 유추해 사실로 등록하지 않는다. `aliases`는 띄어쓰기·표기 변형을 대응시키기 위해 제안한 별칭이며 팀 확인이 필요하다. 예를 들어 `카페라테`는 ID 3에 연결하지만, `라떼`만으로는 ID 2·3·4 중 하나를 확정하지 않는다.

### 값의 의미

- `attributes.milk`: 원재료에 우유가 포함되는지의 확인값. `true`, `false`, 미확인 `null`.
- `attributes.caffeine`: 카페인 포함 여부의 확인값. `noncoffee` 카테고리와 별개다.
- `attributes.sweetness`: 매장에서 정의할 상대적 단맛 분류. 당 함량이나 무당·당도 조절 가능 여부를 뜻하지 않는다.
- `sizes`: 허용 사이즈 코드 배열. `null`은 미확인, `[]`는 사이즈 선택이 적용되지 않는 것으로 확인된 상태다.
- `temperatures: []`: 현 백엔드에 온도 선택이 정의되지 않았다. 데우기 요청의 지원 여부까지 확인된 것은 아니다.
- `option_price_deltas: null`: 옵션별 추가금을 모른다. 임의로 0원을 더해 최종 가격을 확정하지 않는다.
- `availability: null`: 판매·품절 여부 미확인. 메뉴 탐색 결과와 실제 주문 가능 여부는 구분한다.

데모는 음료에 `REGULAR`(보통)·`LARGE`(큰) 사이즈가 있고 베이커리는 사이즈 선택이 없다고 가정한다. 추가금·품절 여부는 데모에서도 생성하지 않는다. 데모의 확인·장바구니 행동 정답은 메뉴와 옵션을 선택하는 **대화상 행동**이며, 실결제 가격 검증이나 실제 주문 실행을 뜻하지 않는다.

## AI가 데이터를 보는 구조

정형 데이터 파일을 디스크에 두는 것만으로 모델이 자동으로 읽지는 않는다. **AI 서버의 프로그램이 파일 또는 메뉴 API를 읽고, 그 내용을 모델 입력에 포함**해야 한다.

```text
키오스크 마이크 → STT → 사용자 문장
                         ↓
AI 서버: 메뉴 데이터 읽기 + 해당 세션의 이전 상태 읽기
                         ↓
SLM 입력: 규칙 + 출력 JSON 구조 + 메뉴 정보 + 직전 질문/후보 + 현재 발화
                         ↓
SLM 출력: 의도 + 바꿀 조건(set) + 해제할 조건(clear) + 재질문 필요 여부
                         ↓
서버: 형식/ID 검증 → 이전 상태 갱신 → 실제 메뉴 조건 검색
                         ↓
후보/미확인 정보/누락 옵션에 맞게 다음 질문 결정 → 화면 + 음성 안내
                         ↓
사용자의 다음 발화로 반복 → 최종 확인 → 백엔드 재검증 → 장바구니
```

### 1. 메뉴 파일을 서버가 읽는다

A4000 컴퓨터에 저장소를 클론하면 이 폴더의 JSON도 코드와 함께 내려받는다. Python은 파일을 다음처럼 읽을 수 있다.

```python
import json
from pathlib import Path

catalog_path = Path(__file__).parent / "menu_catalog.json"
catalog = json.loads(catalog_path.read_text(encoding="utf-8"))
menus = catalog["menus"]
```

설계 검증은 이 파일을 사용한다. 실제 서비스에서는 백엔드 `GET /menus`로 최신 ID·이름·가격·분류·온도를 읽고, 매장이 확인한 확장 속성을 ID로 연결하는 구성이 적절하다. 백엔드를 메뉴 기본 정보의 원본으로 유지하고, 가격이나 이름이 바뀔 때 AI 쪽 사본도 갱신한다. 현재 API에는 레시피 확장 속성이 없으므로 그 정보의 관리 위치는 추가 설계가 필요하다.

### 2. 모델에게 전달할 입력을 만든다

현재 메뉴가 9개이므로 처음에는 메뉴 전체를 모델 입력에 넣는 구성을 사용한다. 별도 벡터 DB 없이 시작할 수 있다. 메뉴가 커지면 서버에서 먼저 후보를 조회하고 필요한 항목만 전달하는 방식으로 확장한다.

모델이 받는 정보는 대략 다음과 같다.

```json
{
  "catalog_status": "needs_store_enrichment",
  "menus": ["실제 코드에서는 9개 메뉴 객체가 들어감"],
  "dialogue_context": {
    "state": {"category": "coffee", "temperature": "ICE", "quantity": 1},
    "candidate_ids": [1, 2, 3],
    "last_question": {"slot": "milk", "text": "우유를 넣은 커피와 우유 없는 커피 중 어느 쪽이 좋으세요?"},
    "awaiting_confirmation": false
  },
  "utterance": "우유 없는 걸로."
}
```

`validate_assets.py`의 `build_messages()`가 실제 JSON과 예시를 읽어 이 입력을 만든다. `expected`, `expected_state_after`, `expected_filter`, `expected_next_action`은 평가용 정답이므로 모델 입력에 넣지 않는다.

```powershell
# ai 폴더의 PowerShell에서 실행: 모델에 보낼 입력만 출력
.\.venv\Scripts\python.exe dialogue_design\validate_assets.py --show-prompt S03
```

이 명령은 입력 JSON을 보여줄 뿐이다. 실제 대화는 `ollama_client.py`가 메뉴·문맥·현재 발화를 로컬 Ollama의 `/api/chat`에 전달한다. 모델은 받은 텍스트를 해석하며 PC 폴더를 직접 탐색하거나 JSON 파일을 알아서 발견하지 않는다. 이 설계의 메뉴 데이터나 사용자 발화를 Hugging Face에 업로드할 필요도 없다.

실행용 스키마에는 `recommendations`가 추가된다. 항목마다 등록 메뉴 ID와 해당 `description`에서 그대로 인용한 `description_quote`가 필요하다. 이 추천은 의미에 따른 후보 순서 제안이며, 컨트롤러가 필수 조건으로 검색한 결과를 통과한 추천만 보여준다. 메뉴 추천 자체를 사용자 선택으로 처리하지 않는다.

### 3. 모델은 기존 상태 전체가 아니라 변경분을 제안한다

위 발화의 기대 출력은 다음과 같다.

```json
{
  "intent": "discover_menu",
  "set": {"milk": "without"},
  "clear": [],
  "clarification": null,
  "evidence": {"milk": "우유 없는"}
}
```

`set`에서 빠진 온도·수량은 서버가 기존 값을 유지한다. `clear`는 사용자가 조건을 해제했을 때만 적용한다. 값이 없다는 이유로 매번 1잔이나 아이스로 기본값을 생성하지 않는다. `clarification: null`은 발화 해석이 명확하다는 뜻일 뿐, 메뉴 속성이 확인됐거나 주문을 실행해도 된다는 뜻은 아니다.

“우유 없는 조건은 취소할게”는 `clear: ["milk"]`다. “우유 들어간 걸로”는 `set: {"milk": "with"}`다. 질문인 “이거 우유 들어가?”를 우유 포함 상품을 주문하겠다는 조건으로 바꾸지 않는다.

사이즈 `REGULAR`·`LARGE`는 현재 시나리오의 초안 코드다. 실제 매장 코드가 정해지면 스키마·데이터·정답을 함께 갱신해야 한다. 형식을 제한하는 JSON Schema를 사용하더라도 해석의 정확도는 별도 검증한다.

### 4. 프로그램이 메뉴 조건을 적용한다

현재 정답 조건과 메뉴 데이터를 비교하는 예제 함수는 `filter_catalog()`다. 결과를 세 가지로 나눈다.

| 결과 | 뜻 | 후속 처리 |
|---|---|---|
| `eligible_ids` | 요청한 필수 조건이 확인된 데이터와 일치 | 후보로 표시하되 선택·판매·가격 검증은 후속 처리 |
| `undetermined_ids` | 불일치는 없지만 요청한 속성에 미확인값이 있음 | 맞는다고 단정하지 않고 정보 확인 |
| `excluded_ids` | 하나 이상의 필수 조건이 확인된 값과 불일치 | 해당 조건의 후보에서 제외 |

실제 데이터에서 커피 ID 1·2·3의 우유 속성은 `null`이다. “우유 없는 커피”를 검색하면 셋 다 `undetermined_ids`다. 상품명이 아메리카노라는 이유로 ID 1을 확정하지 않는다. 데모 속성을 명시적으로 적용한 S03에서는 ID 1만 `eligible_ids`가 된다.

`sweetness_preference`는 선호이므로 현재 필터 예제에서 메뉴를 강제로 제외하지 않는다. 단맛 정보가 확인된 뒤 추천 순서에 반영할 수 있지만 “덜 단”과 “당이 전혀 없음”을 같은 조건으로 취급하지 않는다.

### 5. 대화 상태와 다음 질문을 관리한다

서버가 세션마다 메뉴·조건·직전 질문·후보 순서·최종 확인 대기 여부를 저장한다. 모델의 숨은 기억에 맡기지 않고 다음 호출에도 이 정보를 넣는다. 서로 다른 사용자의 상태가 섞이지 않도록 세션을 분리한다.

- “두 번째 거”는 그 사용자 화면에 실제로 보인 후보 순서로 해석한다.
- “응”은 예/아니오 질문에는 답이 될 수 있지만 “아이스와 핫 중 무엇인가요?”에는 온도를 확정할 수 없다.
- 조건을 수정하면 기존 확인 대기를 해제하고 새 구성으로 다시 확인한다.
- 후보가 여러 개면 후보를 구분할 질문을 선택하고, 메뉴가 선택되면 빠진 필수 옵션을 묻는다.
- 후보가 없더라도 미확인 그룹이 남아 있으면 ‘판매 메뉴 없음’으로 단정하지 않는다.
- 현재의 SLM 출력만으로 주문 API를 호출하지 않는다. 사용자 확인 후 백엔드가 ID·옵션·가격·판매 상태를 검증한다.

`expected_next_action`은 사람이 정한 대화 정책 정답이다. 파일 검증 도구와 별도로 `conversation.py`가 실행 정책을 구현한다. 실제 메뉴 모드는 주어진 필드의 기본 메뉴·온도·수량 선택을 테스트하며, 사용자가 요청하지 않은 미등록 사이즈를 임의로 추가하지 않는다. 크기를 명시하면 미확인 정보로 보류한다. 데모 모드는 등록을 가정한 사이즈와 성분 질문까지 수행한다. 실제 판매·가격 검증은 테스트 장바구니 이후의 별도 구현 범위다.

## 할아버지 대표 시나리오

처음부터 메뉴명을 외우도록 요구하지 않는다. 다음은 **데모 속성 기준**이며 최종 메뉴는 답변에 따라 달라진다.

| 예시 ID | 할아버지 발화 | 추출/상태 변화 | 다음 안내 예시 |
|---|---|---|---|
| S01 | 더운데 시원하고 많이 안 단 거 하나 마시고 싶네. | ICE, 1잔, 덜 단 선호 | 커피가 좋으세요, 다른 음료가 좋으세요? |
| S02 | 커피로 줘. | coffee, 앞선 조건 유지 | 우유를 넣은 커피와 우유 없는 커피 중 어느 쪽이 좋으세요? |
| S03 | 우유 없는 걸로. | milk=without, 데모 후보 ID 1 | 조건에 맞는 아메리카노가 있어요. 이걸로 드릴까요? |
| S04 | 그걸로 할게. | 화면의 단일 후보 ID 1 선택 | 보통과 큰 사이즈 중 어떤 걸로 드릴까요? |
| S05 | 큰 걸로 줘. | LARGE, 앞선 온도·수량 유지 | 아이스 아메리카노 큰 사이즈 한 잔을 담을까요? |
| S06 | 그래, 담아 줘. | 확인 대기 중인 구성을 확정 | 장바구니 반영을 요청할 수 있음. 운영에서는 옵션·가격 검증 필요 |

바로 주문 예시는 D01이다. “아이스 카페 라떼 큰 걸로 두 잔 주세요”에서 메뉴 ID 3·ICE·LARGE·2잔을 한 번에 추출하고 확인 단계로 이동한다. “라떼 한 잔”인 D07은 ID 2·3·4 중 하나로 임의 결정하지 않고 구분 질문을 한다.

## 발화 정답 데이터의 구성

총 40개이며 실제 고령자에게 수집한 음성이나 실제 모델 출력이 아니다. 시나리오와 추출 규칙을 합의하기 위한 사람이 작성한 초기 예시다.

| 그룹 | 개수 | 주요 검증 |
|---|---:|---|
| S01–S06 | 6 | 탐색부터 확인까지 이어지는 대화 |
| D01–D12 | 12 | 직접 메뉴 선택, 9개 메뉴, 수량·별칭, 미등록 메뉴·옵션 |
| U01–U08 | 8 | 온도·수량·크기 수정, 조건 해제, 확인 중 수정, 처음부터 다시 |
| C01–C06 | 6 | 질문에 따른 ‘응’ 해석, 화면의 두 번째 메뉴, 도움 요청·불분명한 입력 |
| G01–G08 | 8 | 데이터 미확인, 조건 충돌, 카페인 오해, 부드러운 선호·미지원 사이즈 |

각 줄은 독립 평가 예시다. `context`에 필요한 이전 상태가 들어 있으므로 순서를 섞어도 해당 문맥을 제공하면 평가할 수 있다. S01–S06은 같은 이야기로 읽을 수 있도록 이전 정답 상태가 다음 입력으로 이어진다.

```text
id / group / catalog             예시 식별자·유형·source 또는 demo
utterance                       현재 사용자 발화
context.state                   이전 선택 상태
context.last_question           직전 질문과 선택지
context.candidate_ids           화면에 실제로 제시한 후보 순서
context.awaiting_confirmation   최종 확인 대기 중인지
expected                        모델 조건 추출 정답
expected_state_after            변경분을 적용한 뒤의 상태 정답(해당 예시)
expected_filter                 메뉴 조건 검색의 정답(해당 예시)
expected_next_action            대화 컨트롤러가 선택해야 할 행동 정답
```

## 모델 실행 없이 데이터 검증하기

저장소의 `ai` 폴더에서 실행한다. 가상환경에 새 패키지를 설치할 필요는 없다.

```powershell
.\.venv\Scripts\python.exe dialogue_design\validate_assets.py
.\.venv\Scripts\python.exe dialogue_design\validate_assets.py --query-example S03
.\.venv\Scripts\python.exe dialogue_design\validate_assets.py --query-example G02
```

S03은 데모 조건으로 ID 1이 선택되고, G02는 원본 미확인 속성 때문에 ID 1·2·3이 판단 보류되는 차이를 볼 수 있다. `--query-example`은 정답 조건을 적용하는 시연이며 모델이 맞혔다는 뜻이 아니다. `--show-prompt`에는 정답이 포함되지 않는다.

메뉴 원본과 스냅샷이 같은지도 확인하려면 Node.js가 설치된 개발 컴퓨터에서 다음 명령을 실행한다.

```powershell
.\.venv\Scripts\python.exe dialogue_design\validate_assets.py --check-backend
```

이 도구는 예시 구조·근거 구절·상태 유지·메뉴 ID·기대 필터 결과·확인 전 장바구니 행동 여부를 검사한다. JSON Schema 전체 표준을 구현하는 범용 검증기나 SLM 평가기는 아니다. 실제 SLM 어댑터에서는 스키마 검증을 별도로 적용한다.

## 후속 구현·평가 순서

1. 매장과 우유·카페인·단맛·사이즈·추가금·판매 상태를 확인해 실제 카탈로그를 완성한다.
2. 별칭과 40개 발화 정답을 팀에서 검토한다. 사투리·STT 오인식·추가 요청 표현을 수집해 확장한다.
3. 연결된 로컬 SLM으로 `evaluate_dialogue.py`와 자유 대화를 실행하고 실제 추출 오류를 측정한다. 정답은 평가기에만 보관한다.
4. 추출 결과·추천·컨트롤러의 재질문을 로그로 검토하고 정책을 개선한다.
5. 실제 백엔드 주문 계약에 온도·사이즈 등을 정의한다. 현재 `POST /orders`는 `menuId`, `quantity`만 처리하므로 옵션을 추가로 전송해도 저장·검증되지 않는다.
6. 텍스트 대화가 검증되면 STT·TTS·화면에 연결하고 A4000에서 전체 응답 시간과 메모리를 측정한다.

평가는 JSON 형식 준수율, 필드별 조건 추출 정확도, 부정·수정 처리, 변경하지 않은 상태 유지, 잘못된 후보 확정, 필요한 재질문, 최종 메뉴·옵션 선택 성공률로 나눈다. 이 폴더의 검증 통과는 데이터 일관성을 확인하는 것이며 SLM의 실제 정확도를 의미하지 않는다.
